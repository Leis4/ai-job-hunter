# Автономный поиск, ранжирование и подготовка заявок

## Поиск

`core/search_strategy.py` формирует запросы из групп (DS/ML, аналитика, data
engineering, AI/LLM, Python/backend, смежные направления) и подтверждённых
навыков. Запросы ротируются между циклами, чтобы не сканировать весь рынок за
один запуск.

| Источник | Как подключён | Статус |
| --- | --- | --- |
| Работа России (`trudvsem`) | официальный open-data API | работает |
| Хабр Карьера (`habr`) | публичные карточки и страницы вакансий | работает |
| Карьера VK (`vk_career`) | публичный поиск `team.vk.company` | работает |
| Карьера МТС (`mts`) | публичный поиск `job.mts.ru`, карточки + Nuxt-описание | работает |
| hh.ru (`hh_api`) | официальный API | выключен: 403 с этого IP, обход не выполняется |
| SuperJob (`superjob`) | официальный API | `not_configured`: нужен `SUPERJOB_API_KEY` |
| RSS/Atom (`feed`) | фиды из конфигурации | включается владельцем |

Состояние каждого источника (`source_state`): последний статус, ошибка, время
запуска, количество карточек. SPA показывает это без «зелёных» фиктивных
интеграций.

## Три категории

`core/scoring.py` сохраняет `eligibility` и добавляет `category`:

- **strong** — обязательные ограничения и порог пройдены;
- **opportunity** — роль близка, но есть пробелы/неопределённость; можно
  подготовить отклик вручную, автоматическая очередь не обязательна;
- **rejected** — подтверждённое критическое несоответствие (жёсткий опыт,
  senior/lead без опыта, лицензия, исключённая категория, несовместимый график).

Обязанности и требования разделены: «внедрять модели в production» — задача,
а не докиванельство прошлого коммерческого опыта. Коммерческий опыт ищется
только в явных требованиях (`коммерческий опыт`, `опыт запуска в production`),
а не в описании обязанностей. Опциональные формулировки («будет плюсом»,
«желательно») игнорируются.

Независимые покиванели: `skill_match`, `career_fit`, `schedule_fit`,
`growth_opportunity`, `experience_gap_years`, `match_score`, `invite_realism`,
`confidence`. `invite_realism` — экспертная оценка, не вероятность приглашения.

## Экономия LLM

Быстрый этап — только Python/SQL. LLM используется для писем, анализа
пограничных вакансий и факт-чека. Письма генерируются только для shortlist,
кешируются, стоимость пишется в ledger AITUNNEL. Бюджет — в настройках.

## Заявки

Состояния: `queued`, `manual_review`, `opening_application`, `form_filling`,
`requires_user_action`, `approved`, `submitted`, `exported`, `blocked`,
`cancelled`. Переходы пишутся в `events`.

`POST /api/queue/{id}/browser-draft` открывает публичную страницу вакансии в
изолированном Playwright-профиле, пытается открыть форму, заполняет только
подтверждённые контакты и письмо, прикладывает резюме, делает скриншот и
останавливается. Финальная кнопка не нажимается, `submitted` не выставляется.
Пример: форма стажировки МТС открыта, телефон заполнен, имя/e-mail требуют
ручного ввода; Хабр в headless возвращает CAPTCHA — статус `blocked`, обход не
выполняется. Скриншот доступен через `/api/drafts/<file>.png`.

`POST /api/queue/{id}/mark-submitted` фиксирует факт отправки только после
явного подтверждения пользователя и только для выгруженного ручного отклика.

`POST /api/prepare/best` готовит до N лучших строгих вакансий (резюме + письмо +
очередь), не отправляя ничего.

## Расписание

Используется существующий `schedule_task.ps1` + `run_cycle.cmd`
(`MultipleInstances IgnoreNew`, лимит 2 часа). Дополнительно `run_cycle`
держит `data/cycle.lock`, поэтому веб-цикл и Task Scheduler не запускают два
тяжёлых прохода одновременно.
